# Investor Relations implementation

Operations opens `/dashboard/ops?tab=investors`; CEO opens `/dashboard/ceo?tab=investors`. Superadmin can access either. Both use `getInvestorDirectory` in `actions/investors.ts`, the same `Investor` collection, and the same directory component. Profiles use `/dashboard/investors/[id]` with a `from` query parameter so the return link keeps the directory's filters and page. Adjacent investor links cross page boundaries while preserving filters and updating the return page.

The directory uses database filtering, sorting, `countDocuments`, and 20-record pagination. Its result count is based on the filtered count; executive metrics and the attention section are based on the full collection. The page defaults to **All Investors**. Search is by investor name, with status, wave, relationship manager, priority and sort filters. It does not seed investors. If ten investors are present in MongoDB, all ten appear on the first page. No screenshot records were inserted because they are not in the repository.

Operations and superadmin can add/edit investors, change status, and record calls, correspondence, meetings, follow-ups, notes and opportunities. Superadmin can configure pipeline statuses and waves. CEO can inspect all records, contact details, available status stages, and full history, but cannot call the write actions: they check the signed session, live active User record and allowed role on the server. `changeInvestorStatus` conditionally updates the previous status and appends an audit event in the same MongoDB update. Concurrent changes require the second writer to refresh and retry. Events store actor name/id, time, remarks, previous/new status and optional activity details. Existing history is never replaced by status changes.

The existing notification SSE only signals unread-count changes, so it cannot guarantee a refresh for investor edits. `InvestorRefresh` additionally calls `router.refresh()` every **15 seconds while the tab is visible** and on visibility return. It re-reads MongoDB through the current server page. Operations edits therefore reach an open CEO view within roughly 15 seconds under normal connectivity; an offline tab catches up when visible again. The refresh does not use hard-coded records or duplicate collections.

There is no investor migration or automatic seed. Production records, including the ten screenshot examples, must already exist in this new collection or be entered by Operations/superadmin. Runtime database content and delivery timing were not verified in this implementation task.
